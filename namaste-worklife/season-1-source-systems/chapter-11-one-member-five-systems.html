2. Why There's No Shared ID

Each system was bought at a different time, by a different team, to do a different job. Nobody designed them to share a key. That's normal in every company. The warehouse's job is to create the shared key.

3. Three Ways to Match

MethodHowExampleConfidence
1. Exact IDOne system stores the other's IDHubSpot nexudus_customer_id = M001; ACT365 cardholder has Nexudus email✅ High
2. Normalised keyClean the text, then match exactly"Green Root Foods Ltd" → greenrootfoods = "GreenRoot Foods" → greenrootfoods🟡 Medium–high
3. FuzzySimilarity score on names/emails"Priya Sharma @pixelchai.co.uk" ≈ "priya @pixelchai.co.uk"🟠 Needs human review

Golden rule: use method 1 wherever possible. Push the business to store IDs across systems (like the HubSpot property in Chapter 10). Methods 2 and 3 are for cleaning up the past, not for running the future.

5. Lab 11.2 — Normalisation Rules in SQL

Here's the BigQuery SQL we'll use in Season 2. Read it now so it feels familiar:

-- Normalise a company name into a matching key
CREATE TEMP FUNCTION company_match_key(name STRING) AS (
  REGEXP_REPLACE(                                   -- 4. drop everything but a-z0-9
    REGEXP_REPLACE(                                 -- 3. drop legal suffixes
      REPLACE(LOWER(TRIM(name)), '&', 'and'),       -- 1+2. lowercase, & → and
      r'\b(ltd|limited|llp|plc|inc)\b\.?', ''),
    r'[^a-z0-9]', '')
);

SELECT
  'Green Root Foods Ltd'          AS original, company_match_key('Green Root Foods Ltd')          AS key  -- greenrootfoods
UNION ALL SELECT
  'GreenRoot Foods',                          company_match_key('GreenRoot Foods')                        -- greenrootfoods
UNION ALL SELECT
  'Kite and Key Recruitment Ltd',             company_match_key('Kite and Key Recruitment Ltd')           -- kiteandkeyrecruitment
UNION ALL SELECT
  'Kite & Key Recruitment',                   company_match_key('Kite & Key Recruitment');               -- kiteandkeyrecruitment

-- Normalise an email: lowercase + trim (never change the local part!)
-- 'Priya.Sharma@PixelChai.co.uk' → 'priya.sharma@pixelchai.co.uk'
-- Domain for company matching: SPLIT(LOWER(email), '@')[OFFSET(1)] → 'pixelchai.co.uk'

⚠️ Normalised keys can create false matches: "Nomad Analytics" and "Nomad Analytics Group" are different companies but close. Always keep a manual override table (owned by a person, documented) for the edge cases.

6. The Grain Problem

Grain = what one row means. Each system has a different grain, and mixing them is the #1 source of wrong numbers:

System / fileOne row =
Nexudus contractsone contract (company × resource × period)
Nexudus membersone person
Nexudus bookingsone booking
NetSuite GLone accounting line (company-level customer)
Act!/HubSpot dealsone opportunity
ACT365 eventsone door tap
Excel budgetone site × month

Example bug: join members (6 GreenRoot people) to contracts (1 GreenRoot contract) on company, then SUM(monthly_price) → £2,700 × 6 = £16,200 "MRR". 💥 The fix: aggregate to the same grain before joining. In the warehouse we'll build facts at a clear grain (for example fct_contract_month, fct_site_month_kpis) and the AI will query those, not raw joins.

Interview Questions

Q: How do you link the same customer across systems that don't share an ID?

"Build a crosswalk table with our own stable key and each system's ID. Match on stored cross-system IDs first, then normalised keys like cleaned company names or email domains, and only then fuzzy matching with human review. Keep a manual override table for edge cases and push the business to store IDs across systems going forward."

Q: What is 'grain' and why does it matter?

"Grain is what one row represents: a contract, a person, a booking, a GL line. Joining tables at different grains duplicates rows, for example joining six team members to one contract multiplies MRR by six. Aggregate to a common grain before joining and document each model's grain."

Q: How would you test an AI assistant that answers business questions?

"Build a golden set of real questions with answers verified by hand against the finance and operational systems, including tricky ones like churn versus upgrades and invoiced versus recognised revenue. Run the assistant against it before launch and on every change, and only go live when accuracy meets an agreed threshold."
