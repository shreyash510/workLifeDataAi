1. A Small Story First

Remember Engineer A from Chapter 03? They built a demo in an afternoon: an LLM, the BigQuery schema pasted into the prompt, and a chat box. Let's watch it in a leadership meeting.

   Leader:  "What was Soho's revenue in September?"
   Demo:    "Soho's revenue in September 2026 was £3,565."

   Finance: "That's not what the ledger says. We closed September at £3,475."

The demo summed Nexudus invoices. Finance's number is recognised revenue in NetSuite, which includes the £90 goodwill credit memo for the AV failure on 24 September (Chapter 09). Both numbers exist. The demo picked one, said it with total confidence, and didn't show its workings.

Nothing crashed. No error appeared. And trust was lost in one sentence. That's the failure the brief warns about: "If it confidently returns a wrong figure, trust is lost."

2. What an LLM Is Good At, and Bad At

Good at ✅Bad at ❌
Understanding messy human questions ("how's Soho looking?")Arithmetic over many rows (it guesses)
Writing SQL that is syntactically correctKnowing your definition of revenue, churn or occupancy
Turning a table of results into a clear paragraphKnowing which of two similar tables is the right one
Asking a clarifying question when told toAdmitting it doesn't know, unless designed to
Following written rules and examplesRemembering facts about your business it was never given

So the design principle for this whole season is:

┌─────────────────────────────────────────────────────────────┐
│   THE LLM TRANSLATES. THE WAREHOUSE CALCULATES.             │
│                                                             │
│   • The LLM turns words into a query, and results into      │
│     words.                                                  │
│   • Every number comes from BigQuery, never from the LLM's  │
│     memory or arithmetic.                                   │
│   • Every definition comes from the semantic layer          │
│     (Chapter 21), never from the LLM's guess.               │
└─────────────────────────────────────────────────────────────┘

3. The Naive Version

   ┌──────────┐   question    ┌──────────────────────────┐   SQL   ┌──────────┐
   │  Leader  │──────────────►│ LLM + "here is the schema │───────►│ BigQuery │
   └──────────┘               │  of every table"          │        │ (all of  │
        ▲                     └──────────────────────────┘        │  it)     │
        │        "Soho's revenue was £3,565"                       └────┬─────┘
        └───────────────────────────────────────────────────────────────┘

It demos beautifully on simple questions. It fails in production because the LLM has to guess the business logic every single time, and guesses differently on different days.

4. Five Ways the Naive Version Goes Wrong

All five of these really happen with the lab data:

#FailureLab exampleWrong answerRight answer
1Wrong source for the metric"Soho revenue, September"£3,565 (Nexudus invoices)£3,475 (NetSuite recognised)
2Grain fan-out: join at the wrong level"GreenRoot's MRR": join members (6 people) to contracts£16,200£2,700
3Wrong definition"How many members churned in 2026?" counting every ended contract3 contracts1 company (Brightline), 2 people. K001 was an upgrade, K006 a transfer.
4Hidden double meaning"Is Soho profitable?""Yes/No" with no basis"Before central costs: −£4,175. After: −£5,175."
5Wrong join key"Soho actual vs budget": join NetSuite Soho to Excel SOHO on textNo rows, so "no budget set"−£5,725 vs budget (−62%)

Look at the pattern. None of these is a SQL syntax problem. Every one is a business knowledge problem. A better LLM doesn't fix them. A better design does: give the LLM tables that are already at the right grain, with the definitions already applied and the keys already joined. That's what the marts from Season 2 and the semantic layer from Chapter 21 are for.

5. The Safe Pipeline: 7 Steps

Here is the pipeline Phase 1 actually runs for every question. We'll use it in every chapter of this season.

   "Is Soho profitable?"
          │
          ▼
   ① UNDERSTAND     Classify the question. Which metrics? Which site? Which period?
          │         Two meanings?     → ask back: "Before or after central costs?"
          │                             (or answer both, clearly labelled)
          │         No period given?  → default to the LAST CLOSED month
          ▼         Open month asked for → answer it, labelled PROVISIONAL

          │         • metric definitions (semantic layer, Ch 21)
          │         • KPI meaning + targets: get_business_context (Ch 22)
          │         • the few tables/columns needed (from ai_safe only)
          ▼

          │                                   site=Soho, month=2026-09)
          │         Fall back to FREE SQL (run_sql) only if no metric fits, and say so
          ▼
   ④ GENERATE       Produce the query
          │
          ▼

StepWhich naive failure it fixes
① Understand (ask back when unclear)#4 hidden double meaning
② Retrieve (definitions, not just schema)#1 wrong source, #3 wrong definition
③ Plan (metric first)#2 grain fan-out, #5 wrong join key, because the metric is pre-built at the right grain with the site mapping already applied

Why the period rule in step ①? Finance numbers for a month keep moving until Finance closes that period in NetSuite (Chapter 09). Look at the lab GL: the meeting-room invoices, the £90 credit memo CN-2609-01, the site-staff journals and the central cost allocations are all dated 30 September, the last day of the month. Ask "Soho revenue for September" on 25 September and you'd get a different number from the one Finance closes with. So when a leader doesn't name a month, the assistant uses the last closed month. When they ask about a month that's still open, it answers, but labels the figure PROVISIONAL and says what usually still changes (late invoices, credit memos, accruals, allocations). When Work.Life's close usually finishes is unknown: that's client question #11.

In our design the LLM reaches the warehouse through exactly three tools, and nothing else. We use these names for the rest of the series:

ToolWhat it doesUsed in step
query_metricsAsks for a governed metric by name, with dimensions, filters and a period. The semantic layer (Chapter 21) writes the SQL.③ (first choice)
run_sqlRuns one read-only SELECT over ai_safe, after the step ⑤ checks. Answers are labelled "Exploratory".③ (fallback)
get_business_contextReturns the KPI cards, glossary entries and dated notes relevant to the question (Chapter 22). Text only: never figures.②

6. Two Styles: Free SQL vs Metric Queries

There are two ways the LLM can talk to the warehouse:

Free SQL (text-to-SQL), tool run_sqlMetric queries (text-to-metric), tool query_metrics
What the LLM writesAny SELECT over the allowed tables"metric + dimensions + filters + period", which the semantic layer compiles to SQL
ExampleSELECT SUM(amount_gbp) FROM fct_gl WHERE …{metric: site_contribution, site: Soho, month: 2026-09}
Flexibility✅ Very high🟡 Only what's been defined
Accuracy🟠 Depends on the LLM's guess every time✅ Same definition every time
Testability🟠 Hard: infinite possible queries✅ Test each metric once
Best forExploration: "which companies booked Brick Lane most?"Board-pack KPIs: revenue, occupancy, churn, contribution

Our design uses both, in a fixed order: metric query first. Free SQL only when no metric fits, and then the answer is labelled "Exploratory: this isn't a governed KPI. Check before you rely on it." Leaders get speed on new questions without ever confusing an exploratory number with a board-pack number.

7. Lab 20.1 — Be the LLM

You are the LLM. You've been given the tables in ai_safe (built in Season 2, Chapters 16 and 17). Write the BigQuery SQL for each question, then check it against the answer. Here are the columns you're allowed to use:

   ai_safe.fct_site_month_kpis   site_code, month_start, mrr_gbp, desks_contracted,
                                 sellable_desks, desk_occupancy, has_finance_actuals,
                                 revenue_gbp, direct_costs_gbp, contribution_gbp,
                                 central_costs_gbp, contribution_after_central_gbp,
                                 budget_revenue_gbp, revenue_vs_budget_gbp,
                                 budget_desk_occupancy, meeting_room_hours
   ai_safe.dim_site              site_code, site_name, ...
   ai_safe.fct_booking           booking_id, booking_date, month_start, site_code,
                                 resource_code, resource_type, company_key,
                                 hours, price_gbp, status

💡 revenue_gbp here is recognised revenue: the NetSuite GL lines with pl_category = 'revenue', credit memos included. The lab mart has no "is this period closed?" column yet; in the real build that flag comes from NetSuite's accounting periods (client question #11), and the AI service adds the PROVISIONAL label from it.

Q1. "Is Soho profitable?" (no month named, so use the last closed month: in this lab, September 2026)

SELECT
  site_code,
  revenue_gbp,
  direct_costs_gbp,
  contribution_gbp,                    -- before central costs
  contribution_after_central_gbp
FROM ai_safe.fct_site_month_kpis
WHERE site_code = 'SOHO'
  AND month_start = DATE '2026-09-01';

-- Expected: SOHO | 3475 | 7650 | -4175 | -5175

Q2. "Which sites are furthest below budget on revenue?"

SELECT
  site_code,
  revenue_vs_budget_gbp                                           AS gap_gbp,
  ROUND(SAFE_DIVIDE(revenue_gbp, budget_revenue_gbp) - 1, 3)      AS gap_pct
FROM ai_safe.fct_site_month_kpis
WHERE month_start = DATE '2026-09-01'
ORDER BY gap_gbp;

-- Expected: SOHO −5,725 (−62%), RDG −300 (−9%)

Q3. "How busy was Brick Lane in September?"

SELECT
  SUM(hours)                         AS hours_booked,
  22 * 10                            AS hours_available,   -- 22 working days × 10 h
  ROUND(SUM(hours) / (22 * 10), 3)   AS utilisation
FROM ai_safe.fct_booking
WHERE resource_code = 'SOHO-MR-BRICK'
  AND status = 'confirmed'
  AND booking_date BETWEEN '2026-09-01' AND '2026-09-30';

-- Expected: 9 | 220 | 0.041  (4.1%)

Now spot the difference. Q1 and Q2 are one-table lookups on a governed mart, so they'd become metric queries. Q3 has a hard-coded assumption (22 days × 10 hours) that the LLM invented. That's exactly the kind of thing that should live in the semantic layer as room_hours_available, defined once by Ops. Chapter 21 fixes this.

8. Guardrails: What the SQL Is Never Allowed to Do

These are checked by code in step ⑤, not by asking the LLM nicely in the prompt. Prompts are suggestions; code is a wall.

RuleHow it's enforced
Read only: no INSERT, UPDATE, DELETE, CREATE, DROPThe service account has no write permission anywhere, plus a statement-type check before running
Only the ai_safe datasetIAM: the account can't even see other datasets (Chapter 26)
No query over N bytesBigQuery maximum_bytes_billed on every job (Chapter 27)
Bounded result sizeAt most 200 rows go back to the LLM (outer LIMIT 200). Bigger results must be aggregated first, and the answer says it was truncated. Leaders ask about sites and months, not row dumps; and every row sent costs tokens (Chapter 27).
Bounded retriesMax 2 fix-and-retry loops, then "I couldn't answer that reliably"
No numbers from memoryAnswer step gets only the result rows; a check flags any number in the answer that isn't in the rows

💡 That last check is cheap and powerful. Extract every number from the drafted answer and confirm each one appears in (or is a simple rounding of) the query results. If the LLM writes "£3,565" and the result says 3475, block it.

Every element has a job. The definition line stops the Ops vs Finance argument from Chapter 02. The period status ("closed") tells a leader whether the number can still move; for an open month it would read PROVISIONAL. Show SQL lets an analyst or Finance audit it. Flag as wrong feeds the golden set (Chapter 25).

Interview Questions

Q: Why not just give an LLM the warehouse schema and let it write SQL?

"Because the hard part isn't SQL syntax, it's business logic: which source is the truth for revenue, what grain to join at, how churn is defined. The LLM has to guess that every time, and its guesses vary. You get answers that look right and are wrong. I'd give it governed metrics and pre-modelled marts, so it chooses rather than invents the logic."

Q: What is the difference between text-to-SQL and text-to-metric?

"Text-to-SQL generates arbitrary SQL. Text-to-metric has the LLM pick a defined metric, dimensions and filters, and a semantic layer compiles the SQL. The second is less flexible but consistent and testable, so I'd use it first for KPIs and fall back to SQL for exploratory questions, clearly labelled."

Q: How do you stop the LLM from inventing numbers?

"Numbers only come from query results. The answer step is given the result rows and nothing else, and a post-check confirms every number in the answer appears in those rows. If the check fails, the answer is blocked or regenerated."

Q: How do you make generated SQL safe to run?

"Enforce it outside the model: a read-only service account that can only see the safe dataset, a statement-type check, a dry run, a maximum-bytes-billed cap, a row limit and bounded retries. Never rely on the prompt alone."
