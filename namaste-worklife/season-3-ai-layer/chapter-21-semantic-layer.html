1. A Small Story First

In a business like Work.Life, the word "revenue" typically ends up defined in several places at once. We don't yet know Work.Life's exact picture (that's client question #10), but a typical one looks like this:

  • A calculated field in the BI tool
  • A dbt model column called revenue
  • A Finance spreadsheet for the board pack
  • Someone's head

Ask "what was Soho's revenue in September?" in the lab and you get three honest answers:

  • £3,040 MRR (Ops, from Nexudus contracts): £2,400 Office 101 + £320 + £320 hot desks. It leaves out meeting rooms, because they're pay-as-you-go, not contracted.
  • £3,565 invoiced: everything billed for September, that is, the MRR plus £525 of meeting-room bookings.
  • £3,475 recognised (Finance, from the NetSuite GL): invoiced minus the £90 goodwill credit memo CN-2609-01 for the AV failure on 24 September. This is the number a site P&L uses.

None of them is "wrong". They answer different questions: how much recurring income is under contract, what did we bill, and what did we actually earn. The danger is a single word, "revenue", silently meaning any of the three. Now add an AI that writes its own SQL, and you have a fifth definition that changes from day to day.

The semantic layer's promise is simple: say it once, in one place, and everyone uses that.

   BEFORE                                    AFTER
   ──────                                    ─────
   Tableau ── revenue = ?                    BI tool (any) ──────┐
   dbt     ── revenue = ?                                        │
   Excel   ── revenue = ?                    AI layer ───────────┼──► SEMANTIC LAYER ──► marts
   AI      ── revenue = (guess)                                  │    revenue = ONE thing
   Head    ── revenue = ?                    Digests/alerts ─────┘    (+ owner, version)

2. What a Semantic Layer Is

It's a translation table between business words and SQL, plus rules about how things combine.

It IS…It is NOT…
A set of definitions in code (usually YAML)A new database
Version-controlled in git, reviewed like codeA wiki page that drifts out of date
Compiled into SQL against the martsA replacement for dbt models (it sits on top of them)
The one place the AI gets definitions fromSomething the AI is allowed to edit
   SOURCES ──► raw ──► staging ──► marts ──► SEMANTIC LAYER ──► consumers
                                   (tables)   (meanings)         (BI, AI, alerts)

   dbt models answer:     "what does one row of fct_site_month_kpis contain?"
   Semantic layer answers: "what is 'site contribution', and how do I slice it?"

3. The Four Building Blocks

BlockMeaningWork.Life example
EntityA thing the business has, with a keysite (site_code), company (company_key). Members exist in the marts (member_key), but member-level data is deliberately not in ai_safe
DimensionA way to slicesite name, city, month, plan type, account group
MeasureA raw aggregation of a columnSUM(amount_gbp) where account group = income
MetricA business KPI built from measuressite contribution = recognised revenue − direct costs

The key idea is that metrics are built from measures, not from scratch. "Contribution" reuses "recognised revenue" and "direct costs". Fix a bug in "direct costs" and contribution is fixed everywhere automatically.

4. Lab 21.1 — Write the Core Metrics

Here's what Work.Life's semantic layer looks like, written in the dbt semantic model / MetricFlow style (dbt is already in their stack). Read it slowly. Every line encodes a decision from Seasons 0 and 1.

# models/semantic/site_month.yml
semantic_models:
  - name: site_month
    description: "One row per site per month. Finance figures from NetSuite,
                  contracts from Nexudus, budget and capacity from Excel."
    model: ref('fct_site_month_kpis')
    defaults:
      agg_time_dimension: month
    entities:
      - name: site
        type: foreign
        expr: site_code
    dimensions:
      - name: month
        type: time
        expr: month_start
        type_params: { time_granularity: month }
      - name: has_finance_actuals     # NULL finance is "no data", not £0
        type: categorical
      # real build: add is_period_closed from NetSuite accounting periods
    measures:
      - name: recognised_revenue
        agg: sum
        expr: revenue_gbp            # recognised: GL, after credit memos
      - name: direct_costs
        agg: sum
        expr: direct_costs_gbp
      - name: central_costs
        agg: sum
        expr: central_costs_gbp
      - name: budget_revenue
        agg: sum
        expr: budget_revenue_gbp
      - name: mrr
        agg: sum
        expr: mrr_gbp
      - name: desks_contracted
        agg: sum
        expr: desks_contracted
      - name: sellable_desks
        agg: sum
        expr: sellable_desks

metrics:
  - name: recognised_revenue
    label: "Revenue (recognised)"
    description: "Income posted to the NetSuite GL for the site and month,
                  after credit memos. THE revenue figure for profitability.
                  Not the same as MRR or Nexudus invoices."
    type: simple
    type_params: { measure: recognised_revenue }
    meta: { owner: Finance, version: "1.2", synonyms: [revenue, takings, turnover, sales] }

  - name: site_contribution
    label: "Site contribution (before central costs)"
    description: "Recognised revenue minus site direct costs. Answers
                  'is the site profitable?' unless the user asks for
                  after central costs."
    type: derived
    type_params:
      expr: recognised_revenue - direct_costs
      metrics: [ { name: recognised_revenue }, { name: direct_costs } ]
    meta: { owner: Finance, version: "1.2" }

  - name: site_contribution_after_central
    label: "Site result after central costs"
    type: derived
    type_params:
      expr: recognised_revenue - direct_costs - central_costs
      metrics: [ { name: recognised_revenue }, { name: direct_costs }, { name: central_costs } ]
    meta: { owner: Finance, version: "1.2" }

  - name: desk_occupancy
    label: "Desk occupancy (contracted)"
    description: "Desks under active contract on the last day of the month
                  divided by sellable desks from the capacity sheet."
    type: ratio
    type_params: { numerator: desks_contracted, denominator: sellable_desks }
    meta: { owner: Operations, version: "1.0", synonyms: [occupancy, utilisation of desks] }

  - name: mrr
    label: "MRR (contracted)"
    description: "Sum of monthly price of active membership contracts.
                  Excludes meeting rooms and one-offs. Not recognised revenue."
    type: simple
    type_params: { measure: mrr }
    meta: { owner: Operations, version: "1.0", synonyms: [recurring revenue, run rate] }

  - name: revenue_vs_budget_pct
    label: "Revenue vs budget (%)"
    type: derived
    type_params:
      expr: recognised_revenue / budget_revenue - 1
      metrics: [ { name: recognised_revenue }, { name: budget_revenue } ]
    meta: { owner: Finance, version: "1.0" }

Your task: add two more metrics yourself.

  1. room_utilisation: hours booked ÷ hours available. Put "hours available" in the model as a column (from opening hours), not a hard-coded 220. That fixes the invented assumption from Lab 20.1 Q3.
  2. revenue_churn: MRR from contracts ended as churn (not upgrade, not transfer) ÷ MRR at the start of the month. Which mart and which column does the churn classification come from?

Check yourself: room_utilisation needs a booking-level model plus an hours-available column per room per day. revenue_churn needs one more mart that the Season 2 lab doesn't have yet: a contract-movements model with a movement_type column (new, upgrade, transfer, churn), built once in dbt from the contract end reasons (end_reason in stg_nexudus__contracts: left = churn; upgrade and transfer are not). That's the classification from Chapter 02. Why it matters: K001 (Pixel Chai moving from a hot desk to Office 101) and K006 (Kite & Key moving from Reading to Soho) both "ended", but the customer stayed and paid more or the same. Counting them as churn would tell leadership they lost three customers when they lost one. For 2026 in the lab, revenue churned is £1,400 (Brightline only).

5. Where Should It Live?

Several tools offer a semantic layer. The brief gives us two strong hints: dbt is already in the stack, and "please do not assume Tableau is fixed".

OptionProsConsFit for Work.Life
dbt semantic models (MetricFlow)Lives next to the dbt models it depends on. Same repo, same review, same tests.Vendor fact (check current dbt plans): the hosted Semantic Layer query API is a dbt Cloud feature. Without it, you need some glue (for example compile metrics to views).✅ Best fit: same place as the marts
Inside the BI tool (Tableau, Looker, Metabase)Easy for analystsTied to a tool that's under review. The AI may not be able to read it.❌ BI tool may change
Separate semantic service (for example Cube)Tool-neutral API for every consumerAnother system to run and pay for🟡 Overkill for 14 sites and a small team
Lightweight: YAML + metric viewsSimplest. The definitions YAML is compiled into BigQuery views in ai_safe (one view per metric family).Less flexible slicing; more views to maintain✅ Good fallback if dbt Cloud isn't wanted

Our recommendation: define metrics in the dbt project (one source, owned in git). Serve them to the AI either through dbt's semantic layer API or by materialising the governed metrics into views in ai_safe. The definitions file is the contract; how it's served is a replaceable detail. That's the same source-agnostic thinking we apply to source systems in Chapter 28.

6. How the AI Uses It

Back to the 7-step pipeline from Chapter 20. The semantic layer feeds steps ② and ③:

   "How's Soho doing vs budget?"
          │
          ▼
   ② RETRIEVE   search metric names, labels, descriptions and synonyms
          │       → recognised_revenue, revenue_vs_budget_pct, site_contribution
          ▼
   ③ PLAN       LLM calls query_metrics with a METRIC REQUEST, not SQL:
          │       { metrics: [recognised_revenue, budget_revenue,
          │                   revenue_vs_budget_pct, site_contribution],
          │         where:   site = 'Soho',
          │         period:  2026-09 }    ← no month named, so the
          │                                 last closed month
          ▼
   ④ COMPILE    the semantic layer turns that into SQL. Same SQL every time.
          ▼
   ⑥ EXECUTE    → 3475 | 9200 | −0.62 | −4175
          ▼
   ⑦ ANSWER     "Soho's September revenue was £3,475, 62% below its £9,200
                 budget. Contribution was −£4,175. [Revenue (recognised) v1.2]
                 · Sep 2026, closed"

Notice the LLM never writes revenue_gbp - direct_costs_gbp. It just says "site_contribution". If Finance changes the definition (say, rates move from direct to central costs), they change one line of YAML, the tests run, and every dashboard and every AI answer updates together.

7. Synonyms: Speaking the Leadership Team's Language

Leaders don't say recognised_revenue. They say "takings", "turnover", "how much did Soho bring in". Synonyms in the meta block help step ② find the right metric.

The synonym list starts small and grows from real questions. Every 👎 on an answer where the wrong metric was picked becomes a synonym fix plus a new golden question (Chapter 25).

8. Who Owns Each Definition?

Chapter 04's RACI said it: the business owns definitions; we only propose them. The semantic layer makes that ownership concrete:

Metric familyOwner (accountable)Changes need
Revenue, costs, contribution, budget varianceFinanceFinance approval on the pull request
Occupancy, MRR, members, churn, room utilisationOperationsOps approval on the pull request
Pipeline, conversionSalesSales approval
Synonyms, descriptionsThe analytics lead (whoever holds that role, our side or theirs), on behalf of the businessReview by the metric owner

Each metric carries owner and version in its meta, and the AI shows them under every answer ("Site contribution, Finance, v1.2"). When a leader questions a number, the answer card already tells them who to ask.

9. A Bonus: It Makes the BI Review Easier

The brief says a review of BI and reporting tooling is running in parallel: "please do not assume Tableau is fixed". If definitions live inside Tableau calculated fields and the review picks a different tool (Looker, Power BI, Metabase or anything else), every calculation has to be rebuilt by hand, and probably some get rebuilt wrong.

If definitions live in the semantic layer, the BI migration becomes "point the new tool at the same metrics". The AI layer and the new BI tool show identical numbers from day one. That's a strong point for our supplier response: the AI project de-risks the BI decision instead of competing with it.

Interview Questions

Q: What is a semantic layer and why does an AI analytics tool need one?

"It's a governed set of business definitions (entities, dimensions, measures and metrics) in code, compiled to SQL. The AI needs one so it picks a defined metric instead of inventing logic each time. That gives the same answer as the dashboards and makes accuracy testable per metric."

Q: Where would you put the semantic layer for a client with dbt and an undecided BI tool?

"In the dbt project, next to the marts, version-controlled and owned by the business. Serve it via the dbt semantic layer or as governed views in the AI's dataset. Not in the BI tool, because that's under review and the AI may not be able to read it."

Q: Finance decides business rates should move from direct to central costs. What changes?

"One mapping in the dbt model or measure definition, approved by Finance, with a version bump. Tests and the golden questions re-run, expected answers are updated with Finance, and every dashboard and AI answer reflects the change together. Nothing in the AI prompts changes."

Q: How do you handle a leader using a word that maps to two metrics?

"Keep synonyms in the metric metadata. Where a word is truly unclear, like 'sales' meaning revenue or won deals, the AI asks back or answers both clearly labelled. Every confusion gets logged and becomes a synonym update and a golden test."
