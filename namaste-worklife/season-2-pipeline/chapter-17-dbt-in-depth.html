1. A Small Story First

Here's a failure that happens on data teams all the time (made up, but realistic). Finance renames a NetSuite location from "Soho" to "London Soho". Nothing errors. The pipeline runs. But our site_mapping seed still says "Soho", so every Soho GL line now has site_code = NULL. Soho's revenue in fct_site_month_kpis drops to nothing. The dashboard shows a gap; the AI cheerfully says "Soho had no revenue in October".

Nobody notices for two weeks. The fix took 30 seconds. The damage to trust took months.

With one test, not_null on fct_gl.site_code, the build would have failed the same morning, with a message pointing at the exact problem, before anyone saw a wrong number.

2. What a dbt Test Really Is

A dbt test is just a SELECT that should return zero rows. Any rows returned = failures. That's it.

TypeWhere you write itGood for
Generic testOne line in a .yml fileunique, not_null, accepted_values, relationships
Singular testA .sql file in tests/Anything custom: golden numbers, reconciliations, composite keys
Unit test (dbt 1.8+)A .yml block with fake input rows and expected outputProving a business rule works, before real data arrives
Source freshnessIn _sources.yml"Was raw data loaded recently?"

Every test can be an error (stop the build) or a warning (report, carry on). Choosing which is a business decision: a wrong revenue figure is an error; a small known difference between two systems might be a warning.

3. Lab 17.1 — Generic Tests on Keys and Relationships

Create models/marts/_marts.yml. This is also where descriptions go (section 8):

version: 2

models:
  - name: dim_site
    description: "One row per site. Maps every system's name for the site."
    columns:
      - name: site_code
        description: "Our site key, e.g. SOHO, RDG."
        tests: [unique, not_null]
      - name: netsuite_location
        tests: [unique, not_null]          # every site must be mapped to finance

  - name: dim_company
    description: "One row per real company: members and CRM-only prospects."
    columns:
      - name: company_key
        tests: [unique, not_null]

  - name: dim_member
    columns:
      - name: member_key
        tests: [unique, not_null]
      - name: company_key
        tests:
          - not_null
          - relationships:
              to: ref('dim_company')
              field: company_key

  - name: member_xref
    columns:
      - name: member_key
        tests: [unique, not_null]

  - name: fct_contract_month
    description: "One row per contract per month in which it is active at month end."
    columns:
      - name: site_code
        tests:
          - not_null
          - relationships:
              to: ref('dim_site')
              field: site_code
      - name: company_key
        tests: [not_null]
      - name: mrr_gbp
        tests: [not_null]

  - name: fct_booking
    columns:
      - name: booking_id
        tests: [unique, not_null]

  - name: fct_gl
    description: "One row per NetSuite GL line, tagged with our site_code and P&L category."
    columns:
      - name: tran_id
        tests: [unique, not_null]
      - name: site_code
        description: "NULL means the NetSuite location is missing from seeds/site_mapping.csv."
        tests: [not_null]                  # the test from the story
      - name: pl_category
        tests:
          - accepted_values:
              values: ['revenue', 'direct_cost', 'central_cost']   # 'other' = unknown account

  - name: fct_site_month_kpis
    description: "One row per site per month. Main table for leadership questions."
    columns:
      - name: site_code
        tests: [not_null]
      - name: month_start
        tests: [not_null]

And on staging, protect the rules that later models depend on, in models/staging/_staging.yml:

version: 2

models:
  - name: stg_nexudus__contracts
    columns:
      - name: contract_id
        tests: [unique, not_null]
      - name: plan_code
        tests:
          - accepted_values:
              values: ['P-HOT', 'P-FLEX10', 'P-OFFICE']   # a new plan must be a conscious decision
      - name: start_date
        tests: [not_null]
  - name: stg_excel__capacity_budget
    columns:
      - name: budget_revenue_gbp
        tests: [not_null]          # catches the renamed column from Lab 13.1
      - name: site_code
        tests:
          - relationships:
              to: ref('site_mapping')
              field: site_code

Run only the tests:

dbt test
# ... PASS unique_dim_site_site_code
# ... PASS not_null_fct_gl_site_code
# ... PASS accepted_values_fct_gl_pl_category__revenue__direct_cost__central_cost

💡 Why accepted_values on plan_code? Because int_contract_months has a case that gives desks to P-OFFICE and P-HOT and 0 to everything else. If Work.Life launches a new "Team Desk" plan, it would silently count as 0 desks. The test turns that silent error into a loud question: "how many desks does the new plan hold?"

4. Lab 17.2 — Singular Tests: Golden Numbers and Reconciliations

Composite keys first. "One row per site per month" is a promise; test it. tests/assert_site_month_kpis_grain.sql:

-- fct_site_month_kpis must have exactly one row per site per month
select site_code, month_start, count(*) as n
from {{ ref('fct_site_month_kpis') }}
group by site_code, month_start
having count(*) > 1

Now the most powerful idea in this chapter: golden tests. These are numbers a human has verified by hand. We did that in Chapters 06, 09 and 11. tests/assert_golden_sep_2026.sql:

-- Golden numbers for September 2026, verified by hand in Ch 06, 09 and 11.
-- Returns a row for every site where the mart disagrees with the verified value.
with expected as (
    select 'SOHO' as site_code, 3040 as mrr_gbp, 6 as desks_contracted,
           3475 as revenue_gbp, 7650 as direct_costs_gbp, -4175 as contribution_gbp,
           -5725 as revenue_vs_budget_gbp
    union all
    select 'RDG', 2700, 6, 2900, 2450, 450, -300
),
actual as (
    select *
    from {{ ref('fct_site_month_kpis') }}
    where month_start = date '2026-09-01'
)
select e.site_code,
       e.mrr_gbp,          a.mrr_gbp          as actual_mrr_gbp,
       e.revenue_gbp,      a.revenue_gbp      as actual_revenue_gbp,
       e.contribution_gbp, a.contribution_gbp as actual_contribution_gbp
from expected as e
left join actual as a using (site_code)
where a.site_code is null
   or a.mrr_gbp               != e.mrr_gbp
   or a.desks_contracted      != e.desks_contracted
   or a.revenue_gbp           != e.revenue_gbp
   or a.direct_costs_gbp      != e.direct_costs_gbp
   or a.contribution_gbp      != e.contribution_gbp
   or a.revenue_vs_budget_gbp != e.revenue_vs_budget_gbp

This is the seed of the brief's launch gate. In Season 3 the same idea grows into a set of golden questions that the AI must answer correctly against actuals before leadership relies on it (Chapter 25). If the data underneath can't pass its golden tests, the AI never stands a chance.

Reconciliation tests compare two systems that should agree. Nexudus says Soho members booked £525 of meeting rooms in September. NetSuite shows £525 invoiced minus a £90 goodwill credit = £435. That difference is real and explained (Chapter 11, Q4), so this test should warn, not fail. tests/warn_meeting_rooms_nexudus_vs_netsuite.sql:

{{ config(severity = 'warn') }}

-- Meeting room revenue: Nexudus bookings vs NetSuite account 4100, per site and month.
-- Known causes of differences: credit memos, timing of invoices. Investigate, don't panic.
with bookings as (
    select site_code, month_start, sum(price_gbp) as booked_gbp
    from {{ ref('fct_booking') }}
    where resource_type = 'meeting_room' and status = 'confirmed'
    group by site_code, month_start
),
ledger as (
    select site_code, month_start, sum(amount_gbp) as ledger_gbp
    from {{ ref('fct_gl') }}
    where account_number = 4100
    group by site_code, month_start
)
select site_code, month_start, b.booked_gbp, l.ledger_gbp, b.booked_gbp - l.ledger_gbp as difference_gbp
from bookings as b
full outer join ledger as l using (site_code, month_start)
where coalesce(b.booked_gbp, 0) != coalesce(l.ledger_gbp, 0)

Expected: dbt test reports 1 warning: SOHO, 2026-09, booked 525, ledger 435, difference 90. Reading reconciles exactly (£200 both sides). ✅ That one warning row is exactly the kind of thing leadership will ask "why don't these match?" about. Now you have the answer ready.

One more sanity test, tests/assert_occupancy_in_range.sql:

-- Desk occupancy outside 0–100% means capacity or desk counting is broken
select site_code, month_start, desk_occupancy
from {{ ref('fct_site_month_kpis') }}
where desk_occupancy < 0 or desk_occupancy > 1

5. Lab 17.3 — Unit Tests for the Business Rules

Golden tests check today's real data. Unit tests check a rule with made-up rows, including cases our lab data doesn't have yet. Add to models/intermediate/_intermediate.yml (needs dbt 1.8 or newer):

version: 2

unit_tests:
  - name: flex_holds_no_desk_and_rolling_contracts_continue
    model: int_contract_months
    given:
      - input: ref('stg_nexudus__contracts')
        rows:
          - {contract_id: X1, company_id: C9, member_id: M9, plan_code: P-FLEX10, resource_code: RDG-HOT,
             site_code: RDG, start_date: 2026-07-01, end_date: 2026-07-31, monthly_price_gbp: 180}
          - {contract_id: X2, company_id: C9, member_id: M9, plan_code: P-HOT, resource_code: SOHO-HOT,
             site_code: SOHO, start_date: 2026-07-15, end_date: null, monthly_price_gbp: 320}
      - input: ref('stg_nexudus__resources')
        rows:
          - {resource_code: RDG-HOT, capacity_people: 15}
          - {resource_code: SOHO-HOT, capacity_people: 20}
      - input: ref('int_month_spine')
        rows:
          - {month_start: 2026-07-01, month_end: 2026-07-31}
          - {month_start: 2026-08-01, month_end: 2026-08-31}
    expect:
      rows:
        - {contract_id: X1, month_start: 2026-07-01, desks: 0, mrr_gbp: 180}   # Flex: MRR yes, desk no
        - {contract_id: X2, month_start: 2026-07-01, desks: 1, mrr_gbp: 320}   # started mid-month: counts
        - {contract_id: X2, month_start: 2026-08-01, desks: 1, mrr_gbp: 320}   # rolling (NULL end): continues

dbt test --select "int_contract_months,test_type:unit"

If someone later "simplifies" the join and forgets the end_date is null case, this test fails instantly, even though no real rolling contract has changed. Unit tests are how you protect definitions from Chapter 02's KPI dictionary.

6. Lab 17.4 — Source Freshness

Tests check that data is right. Freshness checks that it's recent. Our loader from Chapter 14 adds _loaded_at to every raw row. Update models/staging/_sources.yml:

version: 2

sources:
  - name: nexudus
    schema: raw_nexudus
    loaded_at_field: _loaded_at
    freshness:
      warn_after:  {count: 24, period: hour}
      error_after: {count: 48, period: hour}
    tables:
      - name: contracts
        columns:
          - name: contract_id
            tests: [not_null]
      - name: members
      - name: sites
      - name: plans
      - name: resources
      - name: companies
      - name: bookings
  - name: netsuite
    schema: raw_netsuite
    loaded_at_field: _loaded_at
    freshness:
      warn_after:  {count: 24, period: hour}
      error_after: {count: 72, period: hour}     # finance changes slowly
    tables:
      - name: gl_lines
  # ... excel, act, act365 the same way. For Fivetran tables use _fivetran_synced.

dbt source freshness
# raw_nexudus.contracts   PASS  (loaded 2 hours ago)
# Run it 3 days after Lab 14.1 and you'll see ERROR. Re-run load_lab.py → PASS.

Freshness is the answer to the "extractor failed silently" story in Chapter 14. If the Nexudus job stops, this check fails within a day, even if the job itself never reported an error.

7. Lab 17.5 — Break It on Purpose

The best way to trust tests is to watch them catch things. Do each, run dbt build, read the failure, then undo it.

BreakHowWhich test catches it
Finance renames a location (the story)In seeds/site_mapping.csv change Soho to London Soho, then dbt buildnot_null_fct_gl_site_code and the golden test (Soho revenue no longer £3,475)
Someone forgets rolling contractsIn int_contract_months, delete c.end_date is null orUnit test, and golden test (Soho MRR drops to £2,400)
A new plan appearsIn int_contract_months, pretend: change 'P-HOT' to 'P-HOTDESK'Golden test (Soho desks 6 → 4)
Grain bugIn fct_contract_month, add join {{ ref('dim_member') }} using (company_key)Golden test (MRR ×4 at Soho, ×6 at Reading)

Notice how many different mistakes the single golden test catches. That's why a small set of hand-verified numbers is the most valuable test you can write.

8. Documentation: Descriptions the AI Can Read Too

Every description you write in YAML ends up in dbt's documentation site:

dbt docs generate      # builds the docs site from your project + warehouse metadata
dbt docs serve         # opens it in your browser

You get a page per model: description, columns, tests, the SQL, and the lineage graph. This directly answers the brief's "documented and handover ready" principle for the modelling layer.

And there's a bigger reason to write good descriptions now: in Season 3, these same descriptions become context for the AI. When it sees contribution_gbp, it should also see "revenue minus direct site costs (accounts 5000–5999), before central overheads. From NetSuite. NULL when finance actuals are not loaded." A model with no description is a model the AI will guess about. Add to _marts.yml:

  - name: fct_site_month_kpis
    description: >
      One row per site per month. Membership KPIs from Nexudus contracts (active at month end),
      finance from the NetSuite GL by transaction date, budget from the Excel capacity sheet.
    columns:
      - name: mrr_gbp
        description: "Sum of monthly contract prices active on the last day of the month."
      - name: desk_occupancy
        description: "desks_contracted / sellable_desks. Offices hold their capacity, Unlimited Coworking 1, Flex 0."
      - name: revenue_gbp
        description: "NetSuite income (accounts 4xxx) incl. credit memos. NULL if no GL loaded for the month."
      - name: contribution_gbp
        description: "revenue_gbp minus direct site costs (accounts 5000-5999), before central overheads."
      - name: has_finance_actuals
        description: "FALSE means finance numbers are unknown for this month, not zero."

9. Lineage and Selecting Parts of the Graph

Because every model uses ref() and source(), dbt knows the full graph:

 raw_nexudus.contracts ─► stg_nexudus__contracts ─┐
 raw_nexudus.resources ─► stg_nexudus__resources ─┼─► int_contract_months ─► fct_contract_month ─┐
                          int_month_spine ────────┘                              ▲             │
 raw_nexudus.companies ─► stg_nexudus__companies ─┐                              │             │
 raw_act.contacts ──────► stg_act__contacts ──────┼─► int_company_matching ─► dim_company       ├─► fct_site_month_kpis ─► ai_safe
 raw_netsuite.gl_lines ─► stg_netsuite__gl_lines ─┘                                │             │
                          seed: site_mapping ─────────────────────► fct_gl ◄───────┘ ────────────┤
 raw_excel.budget ──────► stg_excel__capacity_budget ─────────────────────────────────────────────┘

That graph is how you answer "where does this number come from?", and "if Nexudus changes, what breaks?". dbt's selection syntax uses it:

CommandMeaning
dbt build --select fct_site_month_kpisJust that model and its tests
dbt build --select +fct_site_month_kpisIt and everything upstream of it
dbt build --select stg_nexudus__contracts+It and everything downstream: "what does a Nexudus change affect?"
dbt ls --select source:nexudus+List every model that depends on Nexudus. Your source-agnostic checklist (Ch 28).

dbt build runs seeds, models and tests in graph order. If a test on a model fails, dbt skips everything downstream of it. That behaviour is what makes the next lab safe.

10. Lab 17.6 — Build the ai_safe Layer

Chapter 15 described three ways to build the brief's "controlled copy". In dbt, it's a folder of models. Add to dbt_project.yml:

models:
  worklife_lab:
    # ... staging, intermediate, marts as before
    ai_safe:
      +schema: ai_safe
      +materialized: view          # option A from Ch 15. Switch to 'table' for option B.

dbt needs unique model names, so each file gets an alias: the file is ai_safe__fct_site_month_kpis.sql, but the BigQuery view is ai_safe.fct_site_month_kpis.

-- models/ai_safe/ai_safe__fct_site_month_kpis.sql
{{ config(alias = 'fct_site_month_kpis') }}
select * from {{ ref('fct_site_month_kpis') }}     -- already aggregated, nothing personal

-- models/ai_safe/ai_safe__dim_site.sql
{{ config(alias = 'dim_site') }}
select * from {{ ref('dim_site') }}

-- models/ai_safe/ai_safe__dim_company.sql
{{ config(alias = 'dim_company') }}
select company_key, company_name, industry, home_site_code, is_member_company
    -- no billing_email, no match keys
from {{ ref('dim_company') }}

-- models/ai_safe/ai_safe__fct_contract_month.sql
{{ config(alias = 'fct_contract_month') }}
select month_start, month_end, site_code, contract_id, company_key,
       plan_code, resource_code, is_office, desks, mrr_gbp
    -- no member_key: questions are about companies and sites, not people
from {{ ref('fct_contract_month') }}

-- models/ai_safe/ai_safe__fct_booking.sql
{{ config(alias = 'fct_booking') }}
select booking_id, booking_date, month_start, site_code, resource_code, resource_type,
       company_key, start_time, end_time, hours, price_gbp, status
from {{ ref('fct_booking') }}

-- models/ai_safe/ai_safe__fct_gl.sql
{{ config(alias = 'fct_gl') }}
select tran_id, tran_date, month_start, site_code, tran_type, account_number, account_name,
       account_type, pl_category, company_key, amount_gbp
    -- no memo, no entity: free text can hide personal details
from {{ ref('fct_gl') }}

What's deliberately not in ai_safe:

Not exposedWhy
dim_member, member_xrefNames and emails of individuals. Leadership questions are about sites and companies.
Door events, cardholdersIndividual movement tracking (Ch 08). A company × week attendance mart could be added later, aggregated.
Act! contactsPersonal contact details
Any HR or payroll detailOut of scope in the brief. Staff cost appears only as the GL total "Site Staff".

Two dbt-bigquery configs make this production-grade (check the dbt-bigquery docs for the exact syntax for your version):

  • grant_access_to on the ai_safe views makes them authorized views, so they can read marts while the AI's service account cannot.
  • grants gives the AI's service account BigQuery Data Viewer on ai_safe only, applied automatically on every build.

And here's the safety net from the story: ai_safe models sit downstream of the golden test's model. If assert_golden_sep_2026 fails, dbt build skips the ai_safe refresh. With +materialized: table (option B), the AI keeps reading yesterday's tables, which passed every test. That's the brief's launch-gate principle, working every single night. 🛡️

11. Model Contracts: A Promise to the AI

A dbt model contract fixes a model's column names and types. If a change would add, remove, rename or retype a column, the build fails. That's exactly what a consumer like an AI layer needs: a stable interface.

# models/ai_safe/_ai_safe.yml
version: 2
models:
  - name: ai_safe__dim_company
    config:
      contract:
        enforced: true
    columns:
      - name: company_key
        data_type: string
      - name: company_name
        data_type: string
      - name: industry
        data_type: string
      - name: home_site_code
        data_type: string
      - name: is_member_company
        data_type: boolean

Contracts are the technical half of the brief's source-agnostic answer. When HubSpot replaces Nexudus as the member source, staging and intermediate models change; the contracted ai_safe models must not. If they would, the build tells you before the AI breaks. We use this in Chapter 28.

12. Exposures, Scheduling and CI

Exposures tell dbt who uses what, so lineage reaches all the way to the consumer:

# models/ai_safe/_exposures.yml
version: 2
exposures:
  - name: phase1_leadership_ai
    type: application
    maturity: low
    description: "Phase 1 natural-language Q&A for the leadership team (Season 3)."
    owner:
      name: Operations & IT Systems
    depends_on:
      - ref('ai_safe__fct_site_month_kpis')
      - ref('ai_safe__dim_site')
      - ref('ai_safe__dim_company')

The nightly run, in order:

   02:00  extract + load (Fivetran syncs, Python jobs)               ← Ch 13, 14
   03:00  dbt source freshness        fail → alert, stop
   03:05  dbt build                   seeds → models → tests, in graph order
              test fails → downstream (incl. ai_safe) skipped → alert
   03:30  ai_safe refreshed only if everything above passed
   later  BI dashboards and the AI read fresh, tested data

CI (continuous integration): every change to the dbt project goes through a pull request, and a CI job runs dbt build against a separate CI dataset before it can be merged. Changes can't reach production without passing every test. dbt Cloud has this built in; with Core, a GitHub Actions workflow does the same.

Interview Questions

Q: How do you make sure a dashboard number stays correct over time?

"Tests at every layer: unique and not-null keys, relationships, accepted values on codes that drive logic, source freshness, and a small set of golden numbers verified by hand, like last month's revenue per site. They run on every build and in CI. If a test fails, downstream models aren't refreshed, so people keep seeing the last good numbers."

Q: What's a golden test?

"A test that compares a model's output to values a person has verified against the real source, for example September revenue per site matching the finance system. It catches many kinds of bugs at once, from broken mappings to grain errors, because they all change the final number."

Q: Two systems disagree on meeting room revenue. Should the test fail?

"It depends whether the difference is expected. Credit notes exist only in finance, so some difference is normal. I'd make it a warning that reports the difference per site and month, document the known causes, and only fail if it exceeds an agreed tolerance."

Q: How do you expose warehouse data to an AI layer without exposing personal data?

"A separate dataset of views or tables built from the marts, selecting only safe columns: no names, emails, free-text memos or individual movement data. The AI's service account can read only that dataset. I'd enforce model contracts on it so its shape stays stable, and refresh it only after all tests pass."
