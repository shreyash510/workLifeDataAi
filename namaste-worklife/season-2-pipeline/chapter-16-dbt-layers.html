1. A Small Story First

Remember Lab 15.1? To get desk occupancy from raw data we wrote one big query with casts, the empty-string rule, the Flex rule, a join to resources and a join to the Excel budget. Now imagine (made-up scenario):

  • The Tableau dashboard has its own copy of that logic.
  • A monthly Excel report has another copy.
  • The AI writes a fresh version every time someone asks.

Then the business decides Flex members should count as 1 desk. Three places to change, and one gets missed. Now the dashboard says 19.4% and the AI says 22.6% for the same site and month. Trust gone. 💔

dbt fixes this by turning every piece of logic into a named, version-controlled SQL model, defined once, that everything else reads.

2. What dbt Is, in One Picture

   YOU WRITE                               dbt DOES                          BIGQUERY GETS
   ─────────                               ────────                          ─────────────
   models/marts/fct_site_month_kpis.sql    1. reads every .sql file          CREATE OR REPLACE TABLE
     select ...                            2. works out the order from        marts.fct_site_month_kpis
     from {{ ref('fct_contract_month') }}     every ref() and source()        AS select ...
                                           3. compiles Jinja → plain SQL
   models/.../_sources.yml                 4. runs them in order             + views, tables, tests
     tests, descriptions                   5. runs tests                     + docs and lineage
dbt wordMeaning
ModelOne .sql file with one SELECT. dbt turns it into a view or table.
{{ source('nexudus', 'contracts') }}Points at a raw table someone else loaded
{{ ref('stg_nexudus__contracts') }}Points at another model. This is how dbt knows the build order.
MaterializationHow a model is built: view, table, incremental, ephemeral
SeedA small CSV in the project, loaded as a table (mapping tables)
MacroA reusable SQL snippet (Jinja function)
TestA query that should return zero rows. Chapter 17.

dbt Core is free and open source: you run it from the command line. dbt Cloud is the paid hosted version with a web IDE and scheduler. Everything in this chapter works with Core. Ask on access day which one Work.Life uses.

~/.dbt/profiles.yml (in your home folder, not in Git, because in real projects it holds credentials):

worklife_lab:
  target: dev
  outputs:
    dev:
      type: bigquery
      method: oauth                 # uses your gcloud login from Chapter 14
      project: mini-worklife-lab    # your project ID
      dataset: dbt_dev              # default dataset (our macro below overrides it)
      location: europe-west2
      threads: 4

macros/generate_schema_name.sql. By default dbt would name datasets dbt_dev_staging, dbt_dev_marts. This macro makes it use exactly staging, intermediate, marts, the datasets we created in Lab 12.2:

{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- if custom_schema_name is none -%}
        {{ target.schema }}
    {%- else -%}
        {{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

⚠️ In a real team, every developer needs their own datasets (e.g. dbt_sam_marts) so they don't overwrite production while working. Keep the default behaviour there, or make this macro use plain names only for the production target. For a solo lab, plain names are simpler.

4. Lab 16.2 — Sources and Staging Models

models/staging/_sources.yml tells dbt where the raw tables are:

version: 2

sources:
  - name: nexudus
    schema: raw_nexudus
    tables:
      - name: sites
      - name: plans
      - name: resources
      - name: companies
      - name: members
      - name: contracts
      - name: bookings
  - name: netsuite
    schema: raw_netsuite
    tables:
      - name: gl_lines
  - name: excel
    schema: raw_excel
    tables:
      - name: capacity_budget_2026
  - name: act
    schema: raw_act
    tables:
      - name: contacts
      - name: opportunities
  - name: act365
    schema: raw_act365
    tables:
      - name: cardholders
      - name: door_events

Staging rules: one model per raw table; rename to clear names; cast types; clean text; turn empty strings into NULL; drop columns nobody should need. No joins, no business logic.

stg_nexudus__contracts.sql, the most important one:

select
    contract_id,
    company_id,
    member_id,
    plan_code,
    resource_code,
    upper(trim(site_code))                              as site_code,
    cast(start_date as date)                            as start_date,
    safe_cast(nullif(end_date, '') as date)             as end_date,          -- '' = rolling
    cast(monthly_price_gbp as numeric)                  as monthly_price_gbp,
    cast(list_price_gbp as numeric)                     as list_price_gbp,
    safe_cast(nullif(notice_given_on, '') as date)      as notice_given_on,
    nullif(end_reason, '')                              as end_reason          -- upgrade / transfer / left
from {{ source('nexudus', 'contracts') }}

select
    cardholder_id,

from {{ source('act365', 'cardholders') }}

-- stg_act365__door_events.sql   (cardholder_name dropped on purpose)
select
    event_id,
    cast(event_time_utc as timestamp)   as event_time_utc,

    door,
    cardholder_id,
    event_type
from {{ source('act365', 'door_events') }}

Notice what staging removed: phone numbers, card numbers and names from door data. Chapter 08 showed door logs are personal data. If nothing downstream needs a sensitive column, the safest place to drop it is the very first model. The brief's "safe data only" starts here, long before the AI layer.

6. Lab 16.4 — Intermediate: Month Spine and Contract Months

Most leadership questions are "per month". But a contract is one row with a start and end date. To answer "MRR in July", we need one row per contract per month it was active. First, a list of months (a "spine"):

-- int_month_spine.sql: one row per month between the two project vars
select
    month_start,
    last_day(month_start)               as month_end
from unnest(generate_date_array(
    date '{{ var("spine_start") }}',
    date '{{ var("spine_end") }}',
    interval 1 month
)) as month_start

Now the key business rule, written exactly once. Our definition (from Chapter 06): a contract counts in a month if it is active on the last day of that month. Desks: offices hold their capacity, Unlimited Coworking holds 1, Flex holds 0.

-- int_contract_months.sql
-- Grain: one row per contract per month in which it is active at month end.
with contracts as (
    select * from {{ ref('stg_nexudus__contracts') }}
),
resources as (
    select * from {{ ref('stg_nexudus__resources') }}
),
months as (
    select * from {{ ref('int_month_spine') }}
)

select
    m.month_start,
    m.month_end,
    c.contract_id,
    c.company_id,
    c.member_id,
    c.site_code,
    c.plan_code,
    c.resource_code,
    c.plan_code = 'P-OFFICE'                       as is_office,
    case c.plan_code
        when 'P-OFFICE' then r.capacity_people     -- an office holds all its desks
        when 'P-HOT'    then 1                     -- unlimited coworking = 1 desk
        else 0                                     -- Flex = day passes, no desk (Ch 06 definition)
    end                                            as desks,
    c.monthly_price_gbp                            as mrr_gbp
from contracts as c
join months as m
  on c.start_date <= m.month_end
 and (c.end_date is null or c.end_date >= m.month_end)     -- the NULL case = rolling contracts
left join resources as r
  on r.resource_code = c.resource_code

If the business ever changes the Flex rule, it's one line, here. Every dashboard and the AI pick it up on the next run.

7. Lab 16.5 — The Company Crosswalk in SQL

Chapter 11 built the crosswalk by hand and showed the normalisation SQL. Now it becomes a macro and a model. macros/company_match_key.sql:

{# 'Kite and Key Recruitment Ltd' and 'Kite & Key Recruitment' -> 'kiteandkeyrecruitment' #}
{% macro company_match_key(column) -%}
    regexp_replace(
        regexp_replace(
            replace(lower(trim({{ column }})), '&', 'and'),
            r'\b(ltd|limited|llp|plc|inc)\b\.?', ''),
        r'[^a-z0-9]', '')
{%- endmacro %}

-- int_company_matching.sql
-- One row per real company, with its name/ID in each system. Includes CRM-only prospects.
with nexudus as (
    select company_id, company_name, {{ company_match_key('company_name') }} as match_key
    from {{ ref('stg_nexudus__companies') }}
),
act as (
    select distinct company_name, {{ company_match_key('company_name') }} as match_key
    from {{ ref('stg_act__contacts') }}
),
netsuite as (
    select distinct entity, {{ company_match_key('entity') }} as match_key
    from {{ ref('stg_netsuite__gl_lines') }}
    where account_type = 'Income'                  -- customers only, not suppliers
),
all_keys as (
    select match_key from nexudus
    union distinct select match_key from act
    union distinct select match_key from netsuite
)

select
    k.match_key,
    n.company_id                          as nexudus_company_id,
    n.company_name                        as nexudus_company_name,
    a.company_name                        as act_company_name,
    ns.entity                             as netsuite_entity
from all_keys as k
left join nexudus  as n  using (match_key)
left join act      as a  using (match_key)
left join netsuite as ns using (match_key)

Expected result: 7 rows. Five member companies (each found in Nexudus, Act! and, except Brightline, NetSuite) plus two CRM-only prospects, Ortho Robotics and Lumen Yoga. The same table you built by hand in Lab 11.1. ✅

8. Lab 16.6 — Dimensions and member_xref

A dimension describes a thing (site, company, member). A fact records something that happened or a measurement (a contract month, a booking, a GL line). Facts point at dimensions by key.

-- dim_site.sql: one row per site, with every system's name for it
with sites as (
    select * from {{ ref('stg_nexudus__sites') }}
),
offices as (
    select site_code, countif(resource_type = 'private_office') as private_offices
    from {{ ref('stg_nexudus__resources') }}
    group by site_code
)
select
    s.site_code,
    s.site_name,
    s.city,
    s.office_desks,
    s.hot_desks,
    s.office_desks + s.hot_desks          as total_desks,
    o.private_offices,
    s.meeting_rooms,
    s.sellable_sqft,
    s.opened_on,
    m.netsuite_location,
    m.act_site_name
from sites as s
left join offices as o using (site_code)
left join {{ ref('site_mapping') }} as m using (site_code)

-- dim_company.sql: one row per real company (members and prospects)
select
    -- OUR key. Anchored on the Nexudus ID today; prospects get a name-based key.
    concat('CO-', coalesce(x.nexudus_company_id, concat('P-', x.match_key))) as company_key,
    x.match_key,
    x.nexudus_company_id,
    coalesce(x.nexudus_company_name, x.act_company_name)  as company_name,
    c.industry,
    c.home_site_code,
    c.billing_email,
    x.act_company_name,
    x.netsuite_entity,
    x.nexudus_company_id is not null                       as is_member_company
from {{ ref('int_company_matching') }} as x
left join {{ ref('stg_nexudus__companies') }} as c
  on c.company_id = x.nexudus_company_id

💡 About that key: CO-C001 is readable and stable while Nexudus exists. But the brief says Nexudus might be replaced, and HubSpot is becoming the member source of truth. In production you'd freeze each key the first time a company appears (a snapshot or a persisted xref table) so it never changes when the source does. That's the heart of Chapter 28.

-- dim_member.sql: one row per person
select
    concat('MB-', m.member_id)          as member_key,
    m.member_id                         as nexudus_member_id,
    c.company_key,
    m.first_name,
    m.last_name,
    m.email,
    m.role,
    m.joined_on,
    m.status
from {{ ref('stg_nexudus__members') }} as m
left join {{ ref('dim_company') }} as c
  on c.nexudus_company_id = m.company_id

And member_xref, the person-level crosswalk from Chapter 11 (member_key | nexudus_id | ... | act_id | act365_id). ACT365 matches on exact email (method 1). Act! uses first.last@ emails, so we match on email domain + normalised full name (method 2):

-- member_xref.sql: one row per member, with their ID in each system
with members as (
    select
        member_id,
        email,
        split(email, '@')[safe_offset(1)]                        as email_domain,
        lower(regexp_replace(concat(first_name, last_name), r'[^A-Za-z]', '')) as name_key
    from {{ ref('stg_nexudus__members') }}
),
act365 as (
    select cardholder_id, member_email
    from {{ ref('stg_act365__cardholders') }}
    where member_email is not null                 -- contractors (e.g. cleaners) have no member
),
act as (
    select
        contact_name,
        split(email, '@')[safe_offset(1)]                        as email_domain,
        lower(regexp_replace(contact_name, r'[^A-Za-z]', ''))    as name_key
    from {{ ref('stg_act__contacts') }}
)

select
    concat('MB-', m.member_id)                 as member_key,
    m.member_id                                as nexudus_member_id,
    m.email                                    as email_normalised,
    h.cardholder_id                            as act365_cardholder_id,
    if(h.cardholder_id is not null, 'exact_email', null)          as act365_match_method,
    a.contact_name                             as act_contact_name,
    if(a.contact_name is not null, 'domain_and_name', null)       as act_match_method
    -- hubspot_contact_id: add when the HubSpot export is in the warehouse (Ch 10)
from members as m
left join act365 as h on h.member_email = m.email
left join act    as a on a.email_domain = m.email_domain and a.name_key = m.name_key

Expected: 14 rows; all 14 members matched to an ACT365 cardholder; 5 matched to an Act! contact (Priya, Daniel, Ravi, Emma, Fatima).

9. Lab 16.7 — Facts: Contracts, Bookings, GL

-- fct_contract_month.sql
-- Grain: one row per contract per month (active at month end). MRR and desks live here.
select
    cm.month_start,
    cm.month_end,
    cm.site_code,
    cm.contract_id,
    c.company_key,
    concat('MB-', cm.member_id)         as member_key,       -- the contract holder
    cm.plan_code,
    cm.resource_code,
    cm.is_office,
    cm.desks,
    cm.mrr_gbp
from {{ ref('int_contract_months') }} as cm
left join {{ ref('dim_company') }} as c
  on c.nexudus_company_id = cm.company_id

-- fct_booking.sql
-- Grain: one row per booking.
select
    b.booking_id,
    b.booking_date,
    date_trunc(b.booking_date, month)   as month_start,
    b.site_code,
    b.resource_code,
    r.resource_type,
    c.company_key,
    concat('MB-', b.member_id)          as member_key,
    b.start_time,
    b.end_time,
    b.hours,
    b.price_gbp,
    b.status
from {{ ref('stg_nexudus__bookings') }} as b
left join {{ ref('stg_nexudus__resources') }} as r using (resource_code)
left join {{ ref('dim_company') }} as c on c.nexudus_company_id = b.company_id

-- fct_gl.sql
-- Grain: one row per NetSuite GL line. Income and expenses both stored as positive amounts,
-- exactly like the lab file; pl_category says which bucket a line belongs to.
with gl as (
    select * from {{ ref('stg_netsuite__gl_lines') }}
)
select
    gl.tran_id,
    gl.tran_date,
    date_trunc(gl.tran_date, month)     as month_start,   -- ⚠ tran date, not accounting period (Ch 09)
    s.site_code,
    gl.netsuite_location,
    gl.tran_type,
    gl.account_number,
    gl.account_name,
    gl.account_type,
    case
        when gl.account_type = 'Income'                     then 'revenue'
        when gl.account_number between 5000 and 5999        then 'direct_cost'    -- site costs
        when gl.account_number between 6000 and 6999        then 'central_cost'   -- allocations
        else 'other'
    end                                 as pl_category,
    c.company_key,                      -- customers only; suppliers stay NULL
    gl.entity,
    gl.memo,
    gl.amount_gbp
from gl
left join {{ ref('site_mapping') }} as s
  on s.netsuite_location = gl.netsuite_location
left join {{ ref('dim_company') }} as c
  on gl.account_type = 'Income'

10. Lab 16.8 — fct_site_month_kpis

This is the table that answers "what is the state of the business?" and "is Soho profitable?". Grain: one row per site per month. Every KPI from Chapter 02 that our lab data supports, in one place:

-- fct_site_month_kpis.sql
-- Grain: one row per site per month. The main table for leadership questions.
with site_months as (
    select s.site_code, s.total_desks, s.private_offices, m.month_start
    from {{ ref('dim_site') }} as s
    cross join {{ ref('int_month_spine') }} as m
),
contracts as (
    select
        site_code, month_start,
        sum(mrr_gbp)                    as mrr_gbp,
        sum(desks)                      as desks_contracted,
        countif(is_office)              as offices_occupied,
        count(distinct company_key)     as active_companies
    from {{ ref('fct_contract_month') }}
    group by site_code, month_start
),
finance as (
    select
        site_code, month_start,
        sum(if(pl_category = 'revenue',      amount_gbp, 0)) as revenue_gbp,
        sum(if(pl_category = 'direct_cost',  amount_gbp, 0)) as direct_costs_gbp,
        sum(if(pl_category = 'central_cost', amount_gbp, 0)) as central_costs_gbp
    from {{ ref('fct_gl') }}
    group by site_code, month_start
),
rooms as (
    select
        site_code, month_start,
        sum(hours)                      as meeting_room_hours,
        sum(price_gbp)                  as meeting_room_booked_gbp
    from {{ ref('fct_booking') }}
    where resource_type = 'meeting_room' and status = 'confirmed'
    group by site_code, month_start
),
budget as (
    select * from {{ ref('stg_excel__capacity_budget') }}
)

select
    site_code,                          -- USING columns: refer to them unqualified
    month_start,

    -- membership (Nexudus): full contract history, so 0 really means 0
    coalesce(c.mrr_gbp, 0)                                       as mrr_gbp,
    coalesce(c.active_companies, 0)                              as active_companies,
    coalesce(c.desks_contracted, 0)                              as desks_contracted,
    coalesce(b.sellable_desks, sm.total_desks)                   as sellable_desks,   -- Excel first
    round(safe_divide(coalesce(c.desks_contracted, 0),
                      coalesce(b.sellable_desks, sm.total_desks)), 4) as desk_occupancy,
    coalesce(c.offices_occupied, 0)                              as offices_occupied,
    sm.private_offices                                           as offices_total,

    -- finance (NetSuite): NULL when no GL was loaded for that month. No data is NOT zero.
    f.revenue_gbp is not null                                    as has_finance_actuals,
    f.revenue_gbp,
    f.direct_costs_gbp,
    f.revenue_gbp - f.direct_costs_gbp                           as contribution_gbp,
    f.central_costs_gbp,
    f.revenue_gbp - f.direct_costs_gbp - f.central_costs_gbp    as contribution_after_central_gbp,

    -- meeting rooms (Nexudus bookings): NULL when no bookings were loaded
    r.meeting_room_hours,
    r.meeting_room_booked_gbp,

    -- budget (Excel)
    b.budget_revenue_gbp,
    f.revenue_gbp - b.budget_revenue_gbp                         as revenue_vs_budget_gbp,
    b.budget_desk_occupancy,
    b.budget_direct_costs_gbp

from site_months as sm
left join contracts as c using (site_code, month_start)
left join finance   as f using (site_code, month_start)
left join rooms     as r using (site_code, month_start)
left join budget    as b using (site_code, month_start)

Pay attention to the NULL vs 0 choices. We have contracts for every month, so "no contracts" really is £0 MRR. But we only have GL lines for September 2026. Reporting July revenue as £0 would be a lie: it would tell the CEO Soho earned nothing. NULL plus has_finance_actuals = false lets the AI say "I don't have finance actuals for July" instead. That honesty is a big part of the accuracy story in Chapter 25.

Interview Questions

Q: What's the difference between ref() and source() in dbt?

"source() points at raw tables loaded by something outside dbt, like Fivetran or a Python job, and lets you add freshness checks. ref() points at another dbt model. dbt uses both to build the dependency graph, so it runs models in the right order and can draw lineage."

Q: What goes in staging versus marts?

"Staging is one model per source table: rename, cast, clean, drop unneeded or sensitive columns, no joins. Marts are business-ready facts and dimensions with a clear grain and stable, source-neutral names, for BI tools and an AI layer. Intermediate models hold reusable logic in between, like expanding contracts into months."

Q: How would you calculate MRR by month from a contracts table that only has start and end dates?

"Generate a month spine, join each contract to every month where it is active, by a clear rule like 'active on the last day of the month', handling NULL end dates for rolling contracts. That gives one row per contract per month, which I sum by site and month. The rule lives in one intermediate model so every report uses it."

Q: Why might you leave revenue as NULL instead of 0 for some months?

"Because zero is a claim: 'we earned nothing'. If finance data for that month isn't loaded or the month isn't closed, the honest value is unknown. A NULL plus a flag lets dashboards and an AI say 'no actuals yet' instead of reporting a false zero."
